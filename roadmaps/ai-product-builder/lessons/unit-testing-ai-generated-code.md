## Testing matters more when you didn't write the code

There's a common assumption that unit tests are least necessary for AI-generated code, because the AI already "knows how to code" and the output looks clean. The opposite is closer to true. A unit test checks a function against a concrete expected result — it doesn't care who wrote the function or how confident it looks. That property is exactly what you need when you can't fully trust your own read of the code, which is the normal situation with anything generated by a tool rather than typed by you line by line.

## Why your own read of generated code is weaker

When you write a function yourself, you build an informal model of it as you go: you remember the assumption that the input list is never empty, you remember why you chose `>=` instead of `>`. That model is what lets you glance at your own code later and trust it. Reading someone else's code — and an AI's output counts as someone else's code for this purpose — doesn't give you that model for free. You're reconstructing intent after the fact, from the shape of the code alone, and a plausible-looking implementation can hide an assumption that's simply wrong. The code compiles, it runs, it even handles the example you tried — and none of that tells you whether it handles the case you didn't think to try.

## Where generated code actually breaks

Generated code tends to fail in a specific pattern: it gets the common case right and the edge case wrong. Ask for a function that calculates an average, and you'll likely get correct arithmetic — and no check for an empty input array, which throws or returns `NaN` instead of a sensible default. Ask for date handling, and you'll get code that works for normal dates and breaks on a leap year or a timezone boundary. This isn't a flaw unique to any one tool; it's a consequence of how these systems are trained, weighted toward the patterns that appear most often. So when you write unit tests for generated code, the ordinary advice to "test your edge cases" stops being a nice-to-have and becomes the main point of the exercise — the happy path was probably fine; the boundary is where to look.

## Letting the AI write the tests, then checking its work

It's tempting to close the loop entirely by asking the same AI tool to write the test suite for the code it just generated. That's a reasonable starting point, but it has a specific failure mode: if the model misunderstood the requirement when writing the function, it can misunderstand it the same way when writing the tests, producing a suite that passes with total confidence while checking the wrong thing. The fix isn't to avoid AI-written tests — it's to read them the way you'd read the code itself, confirming each assertion actually reflects what the feature is supposed to do, not just what the implementation happens to currently return.

## What a failing — or passing — test tells you here

With your own code, a failing test usually means you made a mistake, and a passing test is mildly reassuring. With generated code, a failing test is just as likely to mean the AI misread the requirement as it is to mean you misread its output, so it's worth treating as a genuine open question rather than an assumed bug in your test. And a passing suite is reassuring in proportion to how well the tests actually cover the boundaries discussed above — a thin suite that only re-checks the obvious case will pass on code that's still wrong in exactly the way that matters.
